# Spec 10: Collector-Driven Multi-Track Synchronization and Pure Numeric Precision

**Triage Label**: `ready-for-agent`

---

## Problem Statement

Two subtle architectural and user-experience issues remain in the `leetcode-sh` Study Station:
1. When searching for single or double-digit problem numbers (e.g., `1`), non-problem curriculum topics (e.g., `topic-01-arrays-sliding-window`) and sequence-ordered curriculum items surface as false positives alongside actual algorithm problems because topic numbering prefixes are treated identically to canonical LeetCode problem numbers.
2. In README synchronization, the multi-track solution indexer scans the filesystem directly with raw regular expressions rather than consuming `ProblemCollector` domain models. Furthermore, when writing multi-track solutions across Section 5 tables, it only includes Python solution scripts (`.py`), inadvertently stripping companion Markdown walkthrough notes (`.md`) from multi-track problem table cells.

---

## Solution

1. **Entity-Aware Numeric Search Filtering**: Upgrade `buildSearchMatcher` in `templates/src/scripts/app.js` so that numeric queries strictly distinguish problem entities from documentation/topic entities:
   - For problem entities: evaluate pure numeric tokens strictly against canonical LeetCode problem numbers (`item.lc_num`) and normalized problem titles (with all sequence prefixes stripped).
   - For non-problem curriculum topic entities: evaluate only against full search blobs for text terms or require explicit topic matching.
2. **Collector-Driven Solution Manifest & Note Link Preservation**:
   - Refactor `scripts/sync_readme.py` so that `build_problem_files_index` operates directly on `collector_items` generated by `ProblemCollector`.
   - Ensure the multi-track solution indexer aggregates both `.py` source code and `.md` companion walkthrough notes for all matching problem entities across `top-100/`, `daily-practice/`, and `luffy/`.
   - Remove standalone static mapping tables (`EXTRA_PROBLEM_MAPPINGS`), sourcing all problem metadata directly through domain collector entities.
3. **Search Target Naming Alignment**:
   - Rename DOM search target variables in `app.js` to accurately reflect their generalized candidate role (`firstMatchElement` / `targetNode`).

---

## User Stories

1. As an algorithmic student searching for problem `1` or `3`, I want search results to exclusively return Problem 1 (Two Sum) or Problem 3 (Longest Substring Without Repeating Characters) without showing false-positive topic catalog entries like Topic 01, so that problem discovery is completely accurate.
2. As a learner reviewing curriculum tracks in `README.md`, I want problem rows with multiple solutions across tracks to display clickable links to both their Python solution files and their Markdown companion notes, so that I can easily navigate between code and walkthroughs.
3. As a developer maintaining README synchronization, I want multi-track problem discovery to query `ProblemCollector` directly without redundant filesystem traversals, so that compiler models remain the single source of truth.
4. As an open-source contributor, I want all synchronization scripts to operate without static mapping dictionaries, so that adding new curriculum examples requires zero code adjustments to sync scripts.

## Implementation Decisions

### 1. Pure Problem-Number Isolation in Client Search
- In `buildSearchMatcher` within `templates/src/scripts/app.js`:
  - When a query token is purely numeric (`/^\d+$/`):
    - For items with `type === "problem"`: extract the integer from `item.lc_num` and match against the token integer value. Additionally, test against title tokens with all leading digits and hyphens stripped.
    - For items with `type !== "problem"` (e.g. `topic-*`, `README.md`): exclude pure numeric matching unless the query explicitly contains non-numeric search terms.
  - In `Enter` keydown handler, rename variable `firstProblem` to `firstMatchElement` to clearly reflect that it may resolve to either a `.problem-item` or a `.nav-item[data-key]`.

### 2. Collector-Driven README Multi-Track Indexing
- In `scripts/sync_readme.py`:
  - Refactor `build_problem_files_index(collector_items)` to accept `collector_items: Dict[str, Any]` directly:
    - Iterate over `collector_items.values()` where `type == "problem"`.
    - Extract problem number integer from `item.get("lc_num")`.
    - For each problem entity, collect both `item.get("py_file")` and `item.get("md_file")` if present on disk.
    - Format them into Markdown links (`[`{path}`]({path})`) and associate them with the problem number.
  - In `sync_multi_track_solutions`:
    - Format table cells using the aggregated list of `.py` and `.md` links joined by `<br>`.
  - Remove `EXTRA_PROBLEM_MAPPINGS` completely.

  - Assert that all 175 problem entities and 94 companion notes remain 100% tracked in README without broken links.
